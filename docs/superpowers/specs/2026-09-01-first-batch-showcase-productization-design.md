# 第一批智慧园区展示产品化设计

## 1. 背景与目标

当前项目已经实现园区客服、停车与空间运营指标、场景预检、执行轨迹、审计、反馈和运营计数，但客户首页仅展示告警、专家协作、运营分析和语音四个场景，运营分析推荐问题也没有按业务域组织。治理数据分散在多个接口中，缺少一个能够准确表达当前能力、验证状态和安全边界的产品页面。

本次第一批改造包括三项：

1. 将园区客服纳入服务端场景目录和首页引导演示。
2. 将运营分析推荐问题按能源、停车、空间、设备和告警组织，突出已有停车与空间能力。
3. 增加只读 AI 治理概览，并在运营工作台提供独立“治理中心”页签；首页仅显示安全的治理状态摘要。

目标是产品化组织既有真实能力，不新建第二套分析、审计或状态系统，不使用前端硬编码结果伪装成功。

## 2. 范围与非目标

### 2.1 范围

- 新增 `CUSTOMER_SERVICE` 演示场景、固定启动问题、预检探针和五场景验证脚本契约。
- 首页增加园区客服卡及治理摘要。
- 客服页面支持由服务端目录驱动的一次性引导启动。
- 运营分析推荐问题按五个业务域分组。
- 抽取应用层能力状态服务，供现有能力接口和治理概览共用。
- 将 `OperationsMetrics` 从 Web 层移动到应用层 `operations` 包。
- 新增治理概览应用服务、只读接口、前端服务、类型和治理页面。
- 更新用户文档中与当前实时语音和新增展示能力冲突的内容。

### 2.2 非目标

- 不建设生产身份认证、租户隔离或持久化治理数据库。
- 不把客服接入统一执行事件流；该工作留给后续统一园区助手与工作项设计。
- 不新增停车预测、实时交通调度、房间级空间优化或自动设备控制。
- 不计算当前数据无法准确支持的跨场景成功率、端到端延迟或人工接管率。
- 不创建新的 SQL 生成或报表引擎。
- 不自动触发报修或创建客服工单。

## 3. 架构设计

### 3.1 应用层能力与指标

新增 `operations` 应用包承载可复用的运营状态：

- `OperationsCapabilitiesService` 读取并规范化知识模式、客服回答模式、分析开关、专家协作可用性、语音与本地演示联合开关，返回稳定的能力快照。
- 现有 `OperationsCapabilitiesController` 改为委托该服务，保持 `/api/operations/capabilities` 响应兼容。
- `OperationsMetrics` 及其快照类型从 `web` 包移到 `operations` 包。现有 `/api/operations/metrics` 路径和字段保持兼容。

治理层不得依赖 Web Controller 或 Web DTO。架构测试约束 `governance` 只能依赖应用服务、场景目录和安全的模型类型。

### 3.2 客服演示场景

`ShowcaseScenarioId` 增加 `CUSTOMER_SERVICE`。服务端固定启动问题为“访客停车怎么收费？”，目录项包含：

- 标题：园区客服；
- 业务问题：园区服务如何自动回答并有序转人工？
- 证据：知识引用、服务意图、人工边界；
- 人工边界：报修和知识不足时转人工；
- 能力要求：当前配置的知识检索与客服回答能力。

客服场景始终具备候选能力：Mock 模式可以离线验证，RAG/DashScope 模式验证实际配置的在线链路。无有效预检收据时仍为 `NOT_READY`，不得根据 Bean 是否存在或前端页面是否存在推断 `READY`。

新增 `CustomerServicePreflightProbe`。探针复用当前运行配置的 `KnowledgePort` 和 `CustomerAnswerPort`，但创建临时 `InMemoryCustomerSessionStore` 与 `InMemoryCustomerTicketAdapter`，并使用独立 `CustomerServiceWorkflow` 执行固定知识问题。成功条件全部满足才返回 `PASSED`：

- 回答非空；
- 至少一个有效知识引用；
- 不需要人工接管；
- 不创建客服工单；
- 临时会话可以读取；
- 不改变正式客服工作流的会话数和工单数。

异常类型只写入安全服务端日志，公开结果继续使用固定失败原因。

### 3.3 治理概览

新增 `GovernanceOverviewService` 和安全的快照 DTO。`GET /api/governance/overview` 每次请求即时聚合，不复制或持久化业务数据。快照包括：

- `capturedAt`；
- 场景总数以及 `READY`、`NOT_READY`、`DISABLED` 数量；
- 能力快照：知识模式、回答模式、向量库、分析、专家协作和语音状态；
- 业务计数：工作流总数/完成数、客服会话数、人工工单数；
- 治理计数：知识总数/启用数、反馈总数/正向数、审计记录数；
- 可定义的比率：工作流完成率、正向反馈率；
- 固定边界：进程内状态、演示角色、分析只读、高风险人工确认、非生产控制系统。

比率分母为零时返回 `null`。接口不返回原始问题、回答正文、知识正文、审批评论、审计资源 ID 或身份信息。它与现有 `/api/operations/metrics` 一样只公开安全聚合值。

工作台治理页可以在角色为 `ADMIN` 时额外调用现有 `/api/audit` 显示近期安全审计条目；其他角色不发起该请求。治理概览失败不以静态数字兜底。审计明细失败仅影响明细区域，不清除已加载的治理快照。

## 4. 前端设计

### 4.1 首页

首页场景排序加入 `CUSTOMER_SERVICE`，图标和任务卡沿用现有真实目录规则。只有状态为 `READY` 且 `live=true` 时才能选择和启动。

首页读取治理概览，并以单行摘要展示：已验证场景数、分析只读边界和高风险人工确认。概览失败时显示“治理状态暂不可用”，不阻塞已经通过目录验证的场景启动。

### 4.2 客服引导启动

`WorkbenchView` 与引导类型允许 `customer`。`App.vue` 将 `CUSTOMER_SERVICE` 映射到客服页。

`CustomerServiceConsole` 接收 `active`、`launchRequest` 并复用 `useGuidedLaunch`：

1. 校验问题必须是服务端目录提供的固定问题。
2. 为每次启动生成新的幂等键。
3. 自动发送一次问题并报告 `started` 或 `failed`。
4. 页面隐藏再返回时不重复发送已经接受的请求。
5. 启动失败保留客服页和重试入口。

自动引导只问停车知识，不触发报修。用户必须主动点击或输入报修问题后才允许创建工单。

### 4.3 运营分析推荐问题

推荐问题从字符串数组改为带 `group`、`label` 和 `question` 的展示模型，按以下五组呈现：

- 能源：总量、趋势、排行、目标完成率、基线偏差、空间分布；
- 停车：各区域进场量、各区域停车利用率；
- 空间：各楼宇平均占用人数、能耗与占用人数关系；
- 设备：离线设备数量；
- 告警：告警数量、高风险告警数量。

点击推荐项只将原始问题填入现有输入框，提交后仍完整经过指标解析、查询计划、SQL AST、成本校验和只读执行。

### 4.4 治理中心

工作台新增 `governance` 视图和导航项，所有角色可见。页面包括：

- 场景就绪概览；
- 能力状态矩阵；
- 工作流、客服、知识、反馈和审计聚合指标；
- 固定安全边界；
- 管理员可见的近期审计明细；
- 加载、空样本、部分失败、完整失败和重试状态。

治理页是状态快照，不订阅统一执行轨迹。右侧轨迹栏保持空闲状态，证据条显示“安全聚合快照”。页面支持键盘导航、窄屏单列和减少动态偏好。

## 5. 数据流与失败处理

### 5.1 预检到首页

1. 管理员调用本地演示预检。
2. 客服探针在隔离存储中执行真实知识回答链路。
3. 成功结果写入当前进程的验证注册表。
4. 目录根据验证 TTL 返回 `READY` 或 `NOT_READY`。
5. 首页只渲染目录事实，不自行探测能力。

验证脚本期望五个且仅五个唯一场景。缺失、重复、非 `READY` 或无合法 `verifiedAt` 均失败。缺少在线凭据时明确报告未通过或未执行，不伪装成功。

### 5.2 治理概览

1. Controller 请求治理应用服务。
2. 服务在同一个 `capturedAt` 下读取能力快照、运营指标和场景目录。
3. 服务计算有定义的比率并附加固定边界。
4. Controller 返回安全 DTO。
5. 首页消费最小子集；治理页消费完整聚合值。

任何单个数据源读取异常都使概览请求失败并返回受控错误，不返回半真半假的服务端快照。前端允许治理概览与管理员审计明细分别成功或失败。

## 6. 安全设计

- 客服预检不得写入正式会话和工单存储。
- 自动引导不得提交报修、反馈、审批或其他副作用。
- 治理接口只返回计数、模式、状态、时间和固定边界。
- 审计明细继续要求 `ADMIN`，非管理员不发起请求。
- `X-Demo-Role` 在页面中继续标注为演示权限，不称为生产认证。
- 首页和治理页显著展示进程内状态及非生产控制边界。
- 不展示思维链、Prompt、密钥、知识正文、原始安防数据或敏感身份信息。

## 7. 测试设计

### 7.1 后端

- 客服探针：成功、无引用、转人工、意外建单、回答异常和隔离存储不污染。
- 场景目录：客服 `READY`、`NOT_READY`、固定启动输入、验证过期和公开失败原因。
- 预检服务与 PowerShell 验证器：五个唯一场景契约。
- 能力服务：模式规范化、分析/专家状态、语音与本地演示联合开关。
- 运营指标移动后的字段和接口兼容回归。
- 治理服务：聚合计数、场景状态、零分母 `null`、固定边界和 `capturedAt`。
- 治理 Controller：安全响应和无敏感字段。
- 架构测试：治理层不依赖 Web Controller；Web 层只负责协议映射。

### 7.2 前端

- 首页：客服卡、验证信息、治理摘要、治理失败不阻塞场景。
- 客服：一次性引导启动、重复请求抑制、失败重试、手动报修才建单。
- 运营分析：五组推荐问题、点击填充、提交原始问题。
- 治理页：加载、空样本、部分失败、完整失败、重试、角色切换和管理员审计。
- 工作台：治理导航、证据条和轨迹空闲状态。
- 可访问性：语义标题、状态文本、键盘操作和窄屏布局。

## 8. 验证与验收

自动验证：

```powershell
.\mvnw.cmd test
Set-Location ui
npm run test:unit
npm run build
Set-Location ..
.\scripts\verify-showcase.tests.ps1
```

具备完整本地演示凭据时，再启动完整栈并执行五场景预检。浏览器人工验收覆盖：首页客服启动、手动报修、停车与空间问题、治理角色切换、失败重试和响应式布局。

最终验收要求：三项功能全部来自真实接口和已有安全边界；不存在前端延时模拟、硬编码业务结果或静态成功状态。

## 9. 后续边界

本批完成后，统一园区助手、统一工作项、客服执行事件、能源异常到工单闭环和自动报告仍是独立的后续架构任务，不在本次实现中顺带扩张。
