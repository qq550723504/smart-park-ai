# 智慧园区 RAG 知识库与客服 DashScope 适配设计

## 1. 背景与目标

当前项目已经具备告警、能耗、安防和客服的 Mock 垂直切片，但知识查询仍由 `MockKnowledgeAdapter` 进行确定性的关键词匹配，客服答复也由 `CustomerServiceWorkflow` 内的固定文本生成。项目缺少 Embedding、向量检索、基于检索证据的回答和可验证的引用来源。

本阶段建立一个可替换的 RAG 知识能力：默认保持离线 Mock 行为；显式启用 RAG 时，使用 DashScope EmbeddingModel 和 ChatClient，为客服生成受检索证据约束的回答。告警诊断继续复用同一知识检索端口，不新增第二套园区知识逻辑。

## 2. 范围

### 2.1 包含

- 保留现有 `KnowledgePort` 和 Mock 适配器，默认配置仍不访问网络。
- 增加知识检索结果模型，包含文档 ID、标题和相似度分数；对外只返回安全元数据，不返回知识正文。
- 增加 RAG 知识适配器：使用 DashScope `EmbeddingModel` 生成向量，使用本地进程内向量存储完成相似度检索。
- 从 classpath 知识资源初始化园区停车、访客、能耗和报修文档；知识管理接口在启用 RAG 时更新同一索引。
- 增加 `mock` / `rag` 配置切换；默认是 `mock`，RAG 只在显式配置时启用。
- 增加客服回答端口和 DashScope 实现，使用 `ChatClient` 读取问题与检索上下文，要求模型返回严格 JSON。
- 校验模型返回的答案、人工转接标记、原因和引用文档 ID；模型引用必须是本轮检索结果的子集。
- 检索为空、模型调用失败、模型输出不合法或客服意图为报修时，保持保守转人工行为。
- 客服会话检索轨迹继续只保存安全查询词、文档 ID 和时间，不保存模型提示词、模型原文或知识正文。
- 为 Mock 检索、RAG 检索、引用校验、模型失败、客服 HTTP 响应和配置切换增加离线测试；真实 DashScope 调用仍只由显式 smoke test 验证。

### 2.2 不包含

- 本阶段不引入 PostgreSQL、pgvector、Redis 或外部知识库。
- 本阶段不实现用户认证、租户隔离、人工坐席系统和真实园区系统接入。
- 本阶段不改变安防的脱敏边界，不接收摄像头、门禁、人员原始数据，也不增加设备控制工具。
- 本阶段不让 Agent 创建工单；工单副作用仍由确定性的客服工作流控制。
- 本阶段不改变告警工作流的风险门禁规则，只替换其可选的知识检索实现。

## 3. 设计方案

### 3.1 配置与 Bean 选择

配置增加以下语义：

```yaml
smartpark:
  knowledge:
    mode: mock
  customer-service:
    answer-mode: mock
```

`mock` 是默认值，沿用现有 Mock 知识和固定客服答复，所有单元测试不需要 API Key。`rag` 知识模式要求 DashScope EmbeddingModel；`dashscope` 客服回答模式要求 ChatModel。RAG 模式和 DashScope 答复模式可以独立切换，便于分别学习检索和生成。

配置错误必须在启动时给出清晰错误，不能静默退回 Mock，避免用户误以为已经调用了真实模型。未启用对应模式时，不创建对应的外部模型适配 Bean。

### 3.2 知识检索边界

保留 `KnowledgePort.search(String)` 作为兼容入口，并增加带相似度的检索能力。推荐通过默认方法或独立扩展接口向上兼容现有告警工具和管理接口：

```text
KnowledgePort
  ├─ MockKnowledgeAdapter
  └─ RagKnowledgeAdapter

KnowledgeMatch
  ├─ KnowledgeDocument document
  └─ double score
```

Mock 适配器为关键词命中返回稳定的演示分数；RAG 适配器返回向量相似度分数。两种实现都必须只返回启用的知识文档，并限制 Top-K、查询长度和文档上下文长度。

RAG 适配器在启动时加载 classpath 中的种子文档，并通过同一索引处理知识管理的新增和启停操作。索引更新失败不得留下半更新的公开状态；管理接口应返回明确错误。知识正文只在内部构造模型上下文，不进入响应 DTO、审计记录或检索轨迹。

### 3.3 客服回答流程

客服流程保留现有确定性的意图识别、会话、幂等和工单边界，变化集中在“有证据时如何生成答复”：

```text
问题
  -> 意图识别
  -> KnowledgePort 检索
  -> 无证据 / 报修 -----------------> 创建人工工单
  -> 有证据
       -> mock answer-mode ----------> 现有固定安全答复
       -> dashscope answer-mode -----> ChatClient 结构化回答
  -> 校验引用属于检索结果
  -> 保存安全结果和检索轨迹
```

DashScope 客服回答模型只接收：用户当前问题、确定性的意图、经过长度限制的检索文档上下文和允许的回答规则。系统提示词要求：只能依据上下文回答；无法确认时请求人工；不得索取或复述身份证、手机号、人脸、原始门禁记录等敏感信息；不得执行设备控制；只返回约定 JSON。

回答契约如下：

```json
{
  "answer": "non-empty string",
  "needsHuman": false,
  "reason": "SUPPORTED | INSUFFICIENT_EVIDENCE | POLICY_LIMIT",
  "citationIds": ["KB-PARKING-001"]
}
```

服务端强制执行以下规则：

- `answer` 必须非空且不超过公开响应限制。
- `citationIds` 必须是本轮检索结果中的文档 ID，不能接受模型自造 ID。
- `needsHuman=true` 时必须创建客服工单；`needsHuman=false` 时不得创建工单。
- 检索为空、引用不匹配、模型超时、调用失败或 JSON 校验失败，都转人工，不返回未经验证的模型文本。
- 报修继续直接转人工，不让模型生成维修承诺。

客服领域结果增加安全的知识引用元数据（文档 ID、标题、分数），现有 `knowledgeSources` 字段保持兼容；对外不返回正文。

### 3.4 告警诊断复用

告警工作流继续依赖 `KnowledgePort` 和现有 `ParkKnowledgeTool`。在 RAG 模式下，它使用同一检索适配器；在 Mock 模式下行为不变。第一期不把检索分数直接交给模型作为可信度，不改变风险门禁；无知识结果仍由现有规则触发证据不足审批。

## 4. 错误处理与安全边界

- DashScope API Key 仍只从环境变量读取，不能写入代码、配置文件、测试输出或文档。
- 不记录完整 Prompt、模型原文、用户原始问题或知识正文；异常只记录固定分类和关联资源 ID。
- 对模型上下文实施文档数量、文档字符数和问题长度上限，避免无限扩大请求。
- 对知识文档中的指令性文本按普通资料处理，系统规则优先；模型不能通过知识正文获得工具调用或设备控制能力。
- 向量检索异常包装为知识服务错误；客服工作流把该错误映射为人工转接，告警工作流沿用现有失败/证据不足语义。
- 关闭 RAG 或 DashScope 答复模式时，应用仍能在无 Key、无网络环境下启动并通过完整测试。

## 5. 测试与验收标准

### 5.1 单元测试

- Mock 和 RAG 检索都只返回启用文档，Top-K、分数范围和空结果行为稳定。
- RAG 适配器使用假的 EmbeddingModel 和假的 VectorStore，测试不访问网络。
- 结构化客服模型输出接受合法引用，拒绝未知引用、缺字段、多字段、错误类型和超长答案。
- 模型异常、超时和无证据都创建 `WAITING_AGENT` 工单。
- 报修、幂等重试、会话追问和工作流原有行为不回归。
- 对外 DTO、会话检索轨迹和审计记录不包含知识正文、Prompt 或模型原文。

### 5.2 集成验证

- 默认 `mock` 配置下 `mvnw test` 全部通过，无真实网络调用。
- 显式 `smartpark.knowledge.mode=rag` 且提供测试替身时，Spring 容器可以启动并完成索引初始化。
- 显式 DashScope smoke test 只验证一次真实回答非空，不输出 Key 或完整响应。
- README 和架构文档说明配置切换、环境变量、安全限制和本地向量存储的生命周期。

## 6. 后续迁移路径

本阶段的 RAG 端口和回答端口必须保持与存储实现解耦。后续接入 PostgreSQL/pgvector 时，只替换向量存储适配器和文档索引持久化，不改客服工作流、告警工作流或对外 DTO。跨实例部署时，再统一处理向量索引、会话、工单、幂等和 Graph checkpoint 的事务与一致性。
