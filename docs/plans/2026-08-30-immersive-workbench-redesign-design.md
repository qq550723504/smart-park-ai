# 沉浸式运营工作台统一改造设计

日期：2026-08-30
状态：已确认设计方向，待实施计划评审

## 1. 背景与问题

当前产品存在两套割裂的视觉与交互体系：

- 展示首页使用深色沉浸式场景、青蓝/紫色光效和玻璃面板。
- 运营工作台及五个业务场景使用浅色薄荷绿卡片体系。
- 首页主题变量局限在 `.showcase-home` 内，工作台无法复用。
- `ui/src/styles.css` 同时承载壳层、告警、客服等多个场景样式，体积和职责过于集中。
- “开始现场演示”和“进入运营工作台”最终都只切换到同一个工作台视图，前者没有真正启动演示，入口语义与实际行为不一致。

本次改造需要从主题、壳层和入口模型三个层面统一，而不是给现有浅色页面追加一层颜色覆盖。

## 2. 已确认决策

1. 采用完整的沉浸式工作台布局，而非仅调整颜色和字体。
2. 右侧“执行轨迹”在桌面端保持固定可见。
3. 首页作为唯一视觉基准，不创造另一套色板、圆角或光效。
4. 保留现有业务能力、API 和核心组件状态，不重写后端业务逻辑。
5. 明确区分两个入口：
   - “开始现场演示”进入指定场景的引导模式，并自动触发该场景的第一步。
   - “进入运营工作台”进入告警工作流总览，但不自动执行。

## 3. 目标与非目标

### 3.1 目标

- 首页、工作台壳层和全部场景页面形成连续一致的视觉体验。
- 用户切换场景时，导航、执行轨迹、身份和系统状态保持稳定。
- 关键执行过程、证据引用、审批状态始终可追踪。
- 消除“现场演示”和“运营工作台”入口行为相同的问题。
- 建立可复用主题变量与基础组件，降低继续扩展场景时的样式成本。
- 桌面、平板和手机宽度下均保持主流程可用。

### 3.2 非目标

- 不改变后端 API 协议和智能体执行语义。
- 不新增业务场景、路由或数据源。
- 不重新设计首页的品牌语言。
- 不为了视觉统一删除现有功能或隐藏关键状态。
- 不引入新的重型 UI 框架；继续使用 Vue、Element Plus 和现有图标资源。

## 4. 信息架构与页面骨架

### 4.1 桌面布局

工作台采用三层结构：

1. 顶部悬浮导航栏
   - 品牌标识与当前场景名称。
   - 场景切换导航。
   - 演示角色、系统状态和返回首页操作。
2. 中部沉浸式分屏
   - 左侧为场景主舞台，占可用宽度的主要部分。
   - 右侧为固定执行轨迹栏，宽度约 340–380px。
3. 底部证据带
   - 展示当前场景的数据来源、运行模式、可信状态和最近事件。
   - 作为全局摘要，不取代右侧详细轨迹。

顶部导航与右侧轨迹属于工作台壳层；告警、客服、语音、专家协作和运营分析只提供主舞台内容与各自的证据摘要。

### 4.2 场景主舞台

每个场景统一采用以下层级：

- 场景眉题：能力类别与当前运行模式。
- 主标题：当前任务或业务目标。
- 状态摘要：风险、置信度、数据新鲜度或连接状态。
- 主操作区：保留各场景已有核心交互。
- 次级信息区：时间线、引用、诊断依据、结果或工单。

场景之间统一视觉骨架，但不强行统一业务内容结构。例如语音场景保留实时交互特性，运营分析保留图表密度，客服保留对话流。

### 4.3 响应式行为

- `>= 1280px`：左侧主舞台 + 固定右侧轨迹栏。
- `768px–1279px`：主舞台单列，轨迹栏移到主内容下方并限制最大高度。
- `< 768px`：顶部导航可横向滚动或收起；摘要卡单列；轨迹栏使用折叠区，但关键等待审批状态默认展开。
- 不允许水平页面溢出；图表和流程图可在自身容器内滚动或缩放。

## 5. 视觉系统

### 5.1 设计变量

直接继承首页现有变量并提升为共享主题：

| 用途 | 值 |
| --- | --- |
| 主背景 | `#06090f` |
| 次级背景 | `#0c111a` |
| 主边框 | `rgba(176, 190, 208, 0.28)` |
| 弱边框 | `rgba(176, 190, 208, 0.16)` |
| 主强调色 | `#70e8ff` |
| 次强调色 | `#8f5cff` |
| 主文字 | `#fff0d2` |
| 次级文字 | `#98a4b6` |
| 警示色 | `#ffd27a` |
| 玻璃背景 | `rgba(4, 7, 12, 0.78)` |
| 强玻璃背景 | `rgba(4, 7, 12, 0.9)` |

共享变量放在工作台与首页共同可访问的主题层中；首页原有类名继续工作，避免一次性破坏现有首页。

### 5.2 组件语言

- 面板：深色半透明背景、18px 左右圆角、细边框、适度模糊和低强度阴影。
- 主按钮：青蓝强调，具备明确 hover、focus、loading 和 disabled 状态。
- 次按钮：透明或深色背景，使用弱边框，不与主操作争抢层级。
- 状态标签：颜色表达状态，文本同时说明状态，不能只依赖颜色。
- 图表：深色画布，网格线与刻度降低对比度，关键序列使用青蓝/紫色/琥珀色。
- 表单：深色输入框和清晰焦点环；Element Plus 通过工作台作用域变量统一覆写。

首页现有园区背景图仅用于需要空间氛围的主舞台背景，不在所有卡片重复铺设，避免内容可读性下降。

## 6. 组件与样式架构

### 6.1 新的共享层

建议建立以下职责边界：

- `showcase-theme.css`：首页与工作台共享的颜色、边框、阴影、间距和状态变量。
- `immersive-workbench.css`：工作台壳层、导航、分屏、证据带和响应式规则。
- `ImmersiveWorkbenchShell.vue`：顶部导航、主舞台插槽、固定轨迹栏和底部证据带。
- 共享基础组件：玻璃面板、状态标签、场景标题和证据项。只有在两个以上页面确实复用时才抽取。
- 场景 CSS：告警、客服、语音、协作、分析各自维护业务布局，消费共享变量。

### 6.2 迁移原则

- 不复制 `showcase-home.css` 到每个页面。
- 不通过大范围 `!important` 强行覆盖浅色主题。
- 先迁移壳层，再按场景迁移；每个场景迁移完成后删除对应旧规则。
- `ui/src/styles.css` 最终只保留必要的全局基础规则或作为迁移入口，业务规则应拆分。
- `analytics.css` 等独立样式改为消费统一主题变量，不保留独立浅色色板。
- 保留现有组件数据流和 composable；视觉组件不得直接调用业务 API。

### 6.3 运行时职责

- `OperationsWorkbench` 继续承担场景选择、角色和启动请求编排，是状态容器而不是纯展示组件。
- `ImmersiveWorkbenchShell` 只负责布局、导航插槽、轨迹插槽和证据带，不感知具体业务 API。
- 引导入口生成 `ScenarioLaunchRequest`，至少包含 `requestId`、`mode`、`scenarioId` 和目标视图。
- 匹配的场景消费一次启动请求，并向工作台报告准备、执行、成功或失败；非目标场景忽略该请求。
- 工作台记录已消费的 `requestId`，防止 `KeepAlive` 激活、响应式重排或视图切换造成重复执行。

## 7. 入口与演示状态模型

### 7.1 入口意图

工作台接收明确的进入意图，而不是只接收 `initialView`：

- `manual`：用户从“进入运营工作台”进入，仅切换视图。
- `guided`：用户从“开始现场演示”进入，携带目标场景与一次性启动请求。

启动请求必须具备唯一标识，确保 Vue `KeepAlive`、重复进入和视图切换不会导致同一个场景被重复自动启动。

### 7.2 引导模式行为

- 进入后显示短暂的“演示准备中”状态。
- 工作台完成挂载、能力检查和场景数据加载后，调用该场景现有的启动动作。
- 启动成功后，右侧轨迹立即订阅对应 runId，并在底部证据带显示运行状态。
- 自动启动失败时保留当前页面，展示可理解的错误和“重新开始”操作，不把用户弹回首页。
- 手动切换到其他场景不会自动启动新场景。

### 7.3 场景启动映射

- 告警工作流：选择默认演示告警并启动工作流。
- 专家协作：使用当前默认演示输入发起协作。
- 运营分析：使用默认分析问题启动分析。
- 实时语音：完成连接准备，但涉及麦克风权限时仍需由用户主动确认，不能绕过浏览器权限模型。
- 园区客服没有首页场景入口，保持手动模式。

## 8. 状态、错误与可访问性

- 所有异步区域必须覆盖空闲、加载、成功、失败和无数据状态。
- 等待审批是高优先级状态，右侧轨迹和主舞台同时给出明确入口。
- 保留语义化 `header`、`nav`、`main`、`aside` 和可读的按钮标签。
- 键盘焦点在首页与工作台切换后落到新页面根节点或主标题。
- 焦点环在深色背景上保持清晰可见。
- 正文与主背景至少满足 WCAG AA 对比度；状态不可只通过颜色区分。
- 动效遵循 `prefers-reduced-motion`，避免持续闪烁或大幅视差。

## 9. 验收标准

### 9.1 视觉

- 在相同 `1440x1000` 视口下，首页与工作台使用同一套颜色、玻璃面板、边框、排版层级和光效语言。
- 五个场景不存在残留的大面积白色或薄荷绿色卡片。
- 右侧执行轨迹在桌面宽度下持续可见，场景切换不重新创建壳层。
- 平板和手机宽度下无页面级水平溢出，关键操作可触达。

### 9.2 行为

- 首页“开始现场演示”会进入选定场景并实际启动第一步。
- “进入运营工作台”不会自动启动业务操作。
- 自动启动最多执行一次；返回首页再开始新的演示可生成新的启动请求。
- 场景切换、返回首页、角色切换、审批、表单和执行轨迹保持可用。
- 实时语音遵守浏览器权限要求。

### 9.3 回归验证

- 前端类型检查、单元测试和生产构建通过。
- 后端现有测试保持通过。
- 使用项目当前 Docker 启动方式完成真实环境验证。
- 在浏览器中对首页与工作台进行同视口截图对比，并逐一检查五个场景。
- 覆盖手动入口、引导入口、重复进入、自动启动失败和响应式布局。

## 10. 风险与控制

- 风险：全局 Element Plus 覆写影响首页或其他组件。
  控制：所有覆写限制在工作台主题作用域内。
- 风险：拆分 `styles.css` 时遗漏旧规则。
  控制：按场景迁移并逐页截图回归，不进行一次性机械删除。
- 风险：`KeepAlive` 导致自动启动重复执行。
  控制：使用唯一启动请求标识和已消费记录。
- 风险：运营分析图表在暗色主题下标签不可读。
  控制：同步调整图表主题配置，而不只调整容器 CSS。
- 风险：固定轨迹栏压缩主舞台。
  控制：在 1280px 以下切换为单列，避免强行保留双栏。

## 11. 实施顺序建议

1. 为入口意图和自动启动补充测试，明确当前行为差异。
2. 提取共享主题变量并建立沉浸式工作台壳层。
3. 迁移顶部导航、固定执行轨迹和底部证据带。
4. 依次迁移告警工作流、客服、语音、专家协作和运营分析。
5. 完成引导模式启动映射和错误处理。
6. 删除已迁移的旧浅色样式并完成全量回归。
